# Cryptography overview

This document explains why and how cryptography is used in the integration between Synapse and a [matrix_auth](https://charmhub.io/synapse/libraries/matrix_auth) charm provider. The focus is on securing sensitive data exchanged during the setup of matrix-based services such as IRC bridges and Maubot plugins.

## Why cryptography is needed

When applications like [IRC bridge](https://charmhub.io/irc-bridge) or [Maubot](https://charmhub.io/maubot) integrate with Synapse (a Matrix homeserver), they need to exchange configuration information that includes sensitive credentials — such as registration secrets. If this data were transmitted as plain text, it would expose the system to serious security risks, especially in distributed environments.

This is especially true when the charm relation crosses model boundaries ([Cross-Model Relations or CMR](https://documentation.ubuntu.com/juju/3.6/reference/relation/#cross-model)). In such cases, the provider side cannot directly access secrets created by the requirer, so an alternative method is required to ensure data confidentiality.

## How cryptography is applied

To solve this, the provider generates a shared encryption key when the relation is created. This key is securely stored as a Juju secret. Both sides — the provider and the requirer — use this key to exchange encrypted data:

- The **requirer** encrypts sensitive registration content before sending it.
- The **provider** decrypts the content using the same shared key.

This ensures that sensitive data is protected even across model boundaries.

Additionally, this key, along with the registration shared secret, is designed to remain stable throughout the lifecycle of the Synapse service — meaning there’s no need for frequent re-generation, reducing risk and overhead.

When the relation is removed and no other component is watching the secret, the encryption key is securely deleted.

## Summary

- Cryptography ensures that sensitive configuration data, like IRC registration details, is never transmitted as plain text.
- A shared encryption key is generated by the provider and used by both sides to encrypt and decrypt this data.
- This approach is especially critical for Cross-Model Relations, where direct access to secrets is restricted.
- Once the relation is no longer needed, unused secrets are automatically cleaned up.
